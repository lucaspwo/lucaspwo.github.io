GPU Passthrough no Mac Pro 6,1 ("trashcan")

FirePro D500 → desktop Linux no monitor físico, via Proxmox

Publicado em 11 de julho de 2026

O objetivo deste guia é passar uma AMD FirePro D500 (GPU Tahiti, arquitetura GCN 1.0, de 2013) de um Mac Pro 6,1 (Late 2013, o “trashcan”) rodando Proxmox VE para dentro de uma VM, com a saída de vídeo aparecendo no monitor físico (HDMI/DisplayPort) — não em VNC/SPICE.

O resultado funciona de ponta a ponta em Linux Mint e Bazzite (Fedora Atomic). No Windows a GPU passa para a VM sem o famoso Code 43, mas o display físico não sai — o motivo está detalhado na seção sobre Windows.

É um problema interessante porque combina duas fontes de peculiaridade ao mesmo tempo: é uma GPU de Mac (vBIOS em EFI GOP, não x86 legado) rodando em hardware de 2013 (sem interrupt remapping na IOMMU). Cada uma dessas características, sozinha, já exige um ajuste específico no passthrough; juntas, exigem uma sequência de passos bem definida para funcionar.

Por que é difícil (e o que cada passo resolve)

As FirePro D500 são GPUs Tahiti (GCN 1.0 / Southern Islands) de 2013, com peculiaridades de Mac. A tabela abaixo resume os obstáculos encontrados e a solução aplicada a cada um:

Obstáculo Sintoma Solução
Mac Pro 6,1 não tem interrupt remapping vfio: Failed to set iommu for container: Operation not permitted allow_unsafe_interrupts=1
GPU de Mac não tem vBIOS x86 (usa EFI GOP) Invalid PCI ROM header signature: got 0xffff; GPU não enumera na VM extrair a vBIOS real e passar como romfile
O amdgpu do host pega a GPU no boot e a “suja” console do host na tela; depois reset recovery - restoring BARs ... blocked, host pode travar early-bind (vfio-pci.ids no cmdline) — prende a GPU ao vfio antes do amdgpu
x-vga=1 / POST da vBIOS de Mac no OVMF sem sinal no boot NÃO usar x-vga; usar vga: none (driver da VM assume)
Driver radeon legado não faz scanout na Tahiti tela preta com sinal forçar amdgpu (amdgpu.si_support=1)
HDMI do Mac é HDMI 1.4 (máx 4K@30) preto com sinal em 4K@60 forçar 1080p/1440p (no Xorg); Wayland/KDE negocia sozinho

Pré-requisitos

  • Proxmox VE 8/9 no Mac Pro 6,1; acesso root por SSH.
  • IOMMU/VT-d disponível (o Xeon E5 v2 do Mac Pro suporta).
  • Uma das duas GPUs livre para a VM.

Atenção: descubra qual GPU alimenta a porta física onde o monitor está — plugue o monitor e veja qual card fica connected:

for s in /sys/class/drm/card*/card*/status; do
  [ "$(cat "$s")" = connected ] && echo "$(dirname "$s"|xargs basename) -> PCI $(readlink -f "$(dirname "$s")/../device"|grep -oE '[0-9a-f]{2}:[0-9a-f]{2}\.[0-9]'|tail -1)"
done

Em um Mac Pro 6,1 típico, o HDMI nativo costuma ser alimentado pela GPU no slot PCI 0000:06:00 (a primária/boot_vga); a outra GPU fica em 0000:02:00. Confirme sempre com o comando acima antes de prosseguir.

Como as duas D500 têm o mesmo device-id (1002:679e), o early-bind por id manda as duas GPUs para o vfio e o host fica headless (administrado por SSH/web). Isso é intencional e desejável aqui.

Descubra os IDs do seu hardware:

lspci -nn | grep -iE "VGA|Display|Audio"
# Referência: GPU 1002:679e (Tahiti LE), áudio HDMI 1002:aaa0, áudio analógico do Mac 8086:1d20 (Cirrus CS4208)
